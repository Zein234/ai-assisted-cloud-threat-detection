# Cloud Threat Detection & AI-Assisted Incident Response

## Overview

This project is a cloud-based security monitoring, threat detection and incident investigation lab built using Microsoft Azure and Microsoft Sentinel.

I started this project with limited practical cybersecurity experience, with the goal of learning how a Security Operations Centre (SOC) detects and investigates suspicious activity in a real cloud environment. The project initially focused on collecting Linux security logs and writing KQL detections, but I gradually expanded it to include Windows telemetry, Sysmon, controlled attack simulations, automated incident collection using Python, and finally an LLM-assisted investigation system that can independently query Microsoft Sentinel for additional evidence.

The final project covers the full process from generating suspicious activity on a cloud workload to collecting the telemetry, detecting it, creating a Sentinel incident, investigating the surrounding activity and generating an incident report.

The main technologies used were:

- Microsoft Azure
- Microsoft Sentinel
- Azure Log Analytics
- Azure Monitor Agent (AMA)
- Kusto Query Language (KQL)
- Linux Syslog
- Windows Security Events
- Sysmon
- Kali Linux
- Python
- Azure SDK for Python
- Ollama / Qwen3
- Google Gemini API
- MITRE ATT&CK


## 1. Azure and Microsoft Sentinel Setup

I started by creating an Azure security lab containing a Log Analytics workspace and enabling Microsoft Sentinel.

The first monitored workload was an Ubuntu Linux virtual machine. I configured the Azure Monitor Agent to collect Syslog events from the VM and send them to the Log Analytics workspace.

Before creating detections, I spent time querying the collected logs using KQL to understand what normal Linux authentication and system activity actually looked like. This was important because I wanted the detections to be based on the telemetry being generated rather than simply copying existing detection queries.


## 2. Linux Detection Engineering

The first detections focused on SSH authentication.

I started by examining successful and failed SSH authentication events and learning how information such as usernames, source IP addresses and source ports appeared inside Syslog messages.

From this I developed detections for:

- Repeated SSH authentication attempts using invalid usernames.
- Successful SSH authentication following multiple failed attempts.
- New Linux user creation.
- Users being granted sudo privileges.

The SSH detections aggregate authentication attempts by source IP and host rather than treating every failed login as a separate alert.

I also configured the detections as Microsoft Sentinel scheduled analytics rules and mapped useful information such as hosts, accounts and IP addresses to Sentinel entities where appropriate.

During this stage I encountered an issue with using fixed time bins for brute-force detection. Attempts occurring only seconds apart could be separated by the boundary between two bins. I changed the detection logic to use overlapping lookback windows and the timestamp of the latest event instead.

For the successful-authentication detection, I correlated failed authentication events with later successful authentication from the same source IP rather than detecting the two behaviours independently.

The detections were tested using controlled SSH activity against the Linux VM. The resulting Sentinel incidents were manually investigated, classified and documented in incident reports.

The detections were also mapped to relevant MITRE ATT&CK techniques, including Brute Force (T1110).


## 3. Windows Security Monitoring

After completing the initial Linux detections, I added a Windows Server VM to the lab.

I configured Windows Security Events collection through the Azure Monitor Agent and began working with the `SecurityEvent` table in Log Analytics.

This introduced Windows security events such as:

- Event ID 4625 - Failed logon.
- Event ID 4624 - Successful logon.
- Event ID 4688 - Process creation.

I created a Windows failed-logon detection that identifies multiple failed authentication attempts from the same source IP within a short period.

While investigating these events I also learnt how fields such as logon type, authentication status/substatus, process name, target account and source IP are needed to understand what a Windows authentication event actually represents. A successful or failed logon event alone is not enough to determine whether activity is malicious.

One of the later incidents was generated by real unsolicited authentication attempts against the Internet-accessible Windows VM. The source attempted authentication against multiple usernames, including accounts that did not exist on the system.

I investigated the surrounding authentication telemetry to determine whether the activity resulted in successful access. No successful authentication from the suspicious source was identified, so the incident was classified as a true positive for suspicious password-guessing/username-enumeration activity, with no evidence of compromise.


## 4. Adding Sysmon

Windows Security Events did not provide all of the telemetry I wanted for more detailed investigations, so I added Sysmon to the Windows VM.

Sysmon provided additional visibility into activity such as process creation, process access, network connections and registry modifications depending on the configured event collection.

This also demonstrated an important part of detection engineering: having a SIEM and collecting logs does not automatically mean that the telemetry required to detect a particular technique is available.


## 5. Registry Persistence Detection

I used a Kali Linux VM as an external system for controlled security testing against the Azure workloads.

I performed another controlled attack simulation based on Windows registry persistence.

A Run registry value was created containing a harmless test command. The activity generated Sysmon Event ID 13 telemetry containing the process responsible for the registry modification, the affected registry location, the value written and the user responsible.

I then created a generalized KQL detection for modifications to the Windows `Run` and `RunOnce` registry locations.

The detection deliberately does not depend on the exact test value, username or process used during the simulation. Instead, it detects the underlying behaviour so that the same rule can identify other programs modifying the same persistence locations.

The detection was mapped to MITRE ATT&CK T1547.001 - Registry Run Keys / Startup Folder.

This completed a full detection-engineering cycle: generate controlled activity, inspect the resulting telemetry, identify the useful fields, create a generalized detection and validate that the detection identifies the behaviour.


## 6. Sentinel Incident Investigation

The analytics rules created throughout the project generated Microsoft Sentinel incidents containing information such as the affected host, source IP, targeted accounts, authentication attempts and MITRE ATT&CK techniques.

Initially, I investigated these incidents manually.

For each incident I reviewed the alert evidence, queried surrounding telemetry using KQL, determined whether additional suspicious activity was present and classified the incident.

I documented the investigations in Markdown incident reports containing:

- Incident overview.
- Alert information.
- Investigation performed.
- Important findings.
- MITRE ATT&CK techniques.
- Incident classification.
- Final conclusion.

The first incident reports were completely manually investigated and written. This manual process was useful for understanding what information an analyst actually needs before attempting to automate the investigation process.


## 8. Python Incident Automation

After manually investigating several incidents, I started automating the process using Python.

I built a Python application using the Azure SDK that connects to Microsoft Sentinel and Log Analytics using Azure authentication.

The application can retrieve active Sentinel incidents and collect information including:

- Incident metadata.
- Sentinel alerts.
- Incident entities.
- Alert custom details.
- MITRE ATT&CK techniques.
- Relevant timestamps and affected resources.

The collected information is converted into structured data that can be used during an investigation.

The application also creates Markdown incident reports so that investigated incidents can be stored as readable security reports rather than remaining only inside the Azure portal.


## 9. AI-Assisted Incident Analysis

The next stage was integrating an LLM into the Python automation.

The first version provided incident information to a locally hosted model using Ollama and Qwen3 14B. The model could analyse the supplied incident and assist with producing the investigation report.

However, I did not want the AI component to simply summarise an alert that Sentinel had already generated. The more useful problem was allowing the model to investigate beyond the original alert.

I therefore changed the system into an iterative investigation process.

The LLM receives the initial incident information and a restricted list of available Log Analytics tables. It can then generate a KQL query requesting additional evidence.

Python executes the query against Log Analytics and returns the real result to the model. The model analyses that evidence and either generates another KQL query or decides that enough evidence exists to produce the final assessment.

This allows the model to progressively investigate an incident rather than receiving a pre-selected collection of logs.


## 10. Grounding and LLM Guardrails

A major part of the AI integration was preventing the model from treating assumptions as evidence.

The investigation system therefore places several restrictions around the LLM.

The model can only query explicitly permitted Log Analytics tables. Before using a table, it can request its schema using KQL so that it can discover the actual available columns rather than relying on assumed schemas.

If the generated KQL is invalid, the Azure query error is returned to the model so that it can correct its query.

Large raw query results are also rejected by the Python application. The model is instead instructed to narrow or aggregate the query, preventing large amounts of raw telemetry from being unnecessarily passed into the LLM.

The investigation prompt also requires the model to distinguish between information directly observed in the incident or telemetry, reasonable interpretations of that evidence, and information that remains unknown.

The intention is not to allow the LLM to decide that an incident is malicious based purely on general cybersecurity knowledge. Cybersecurity knowledge can guide the investigation and generate hypotheses, but conclusions should remain grounded in evidence retrieved from the environment.


## 11. Local vs Cloud LLM Investigation

I initially wanted the investigation system to run locally and tested it using Qwen3 14B through Ollama.

This worked for smaller tasks, but longer investigations exposed limitations including repeated queries, unnecessary changes between telemetry sources, difficulty managing large investigation contexts and inconsistent termination.

Rather than replacing the investigation architecture, I kept the same Python and Sentinel workflow and changed the model backend to Google's Gemini API.

The cloud model showed significantly better behaviour during multi-step investigations, including starting with telemetry overviews, identifying useful activity, correlating discovered identifiers and progressively requesting more specific evidence.

The Gemini implementation uses stateful interactions so that the model retains the investigation history without the Python application manually resending the entire conversation on every request.


## 12. Sentinel Workbook

I also created a simple custom Microsoft Sentinel Workbook to provide a visual overview of the security telemetry collected by the lab.

The workbook supports both the Windows and Linux environments and provides an easier way to explore relevant security activity without manually running every KQL query.

The workbook complements the detection and investigation components by providing an analyst-facing monitoring view of the environment.
